[14:22] ### JDBC
[14:22] - JDBC(Java Database Connectivity): Java 애플리케이션이 DB에 접속해 SQL을 실행하고 결과를 처리하는 표준 API
[14:22] - DB마다(MySQL, MariaDB, Oracle…) 통신 방식과 드라이버는 다르지만, 개발자는 같은 인터페이스(Connection, Statement, PreparedStatement, ResultSet)로 접근한다
[14:22] - 표준 인터페이스: java.sql, javax.sql
[14:22] - 각 DB 회사가 이 인터페이스를 구현한 JDBC 드라이버를 제공 (이 프로젝트: MariaDB Driver, H2)
[14:22] - SQL 문법·벤더 고유 기능만 빼면 코드를 크게 안 바꾸고 다른 DB로 옮길 수 있다

[14:22] 기본 흐름
[14:22] 1. 커넥션 얻기: DataSource(또는 DriverManager)로 Connection을 가져온다
[14:22] 2. SQL 실행: PreparedStatement 등으로 실행 (조회면 ResultSet, 갱신이면 바뀐 행 수)
[14:22] 3. 결과 처리·트랜잭션: 결과를 읽고 필요하면 commit / rollback
[14:22] 4. 자원 반납: ResultSet, Statement, Connection을 닫거나 커넥션 풀에 반납 → 리소스 누수 방지

[14:22] 스프링부트에서는
[14:22] - 순수 JDBC를 매번 쓰기보다 JdbcTemplate, JPA/Hibernate, MyBatis 같은 상위 기술을 주로 쓴다
[14:22] - spring-boot-starter-jdbc나 spring-boot-starter-data-jpa에 HikariCP가 들어 있어서 application.properties에 DB 접속 정보만 적으면 DataSource가 자동 구성된다

[14:22] ### JDBC와 JPA의 차이
[14:22] - JDBC: SQL을 직접 쓰고 실행하는 저수준 표준 API
[14:22] - JPA: Java 객체와 DB 테이블을 매핑해서 SQL 작성을 자동화하는 ORM 표준 명세 (대표 구현체: Hibernate)

[14:22] | 구분 | JDBC (JdbcTemplate) | JPA (Hibernate) |
[14:22] | --- | --- | --- |
[14:22] | 추상화 수준 | 낮음. SQL, 파라미터 바인딩, 결과 매핑을 직접 | 높음. 엔티티 객체 중심, SQL은 프레임워크가 생성 |
[14:22] | 객체-테이블 불일치 | 개발자가 직접 변환 | 연관관계, 상속, 영속성 컨텍스트로 완화 |
[14:22] | 반복 코드 | PreparedStatement, ResultSet 처리가 많음 | Repository, 메서드 이름 규칙으로 CRUD를 크게 줄임 |
[14:22] | 쿼리 제어 | 복잡한 조인·통계·튜닝이 직관적 | 단순 CRUD는 빠르지만 복잡한 쿼리·대량 처리는 보완 필요 |
[14:22] | 오버헤드 | 가볍고 동작 예측이 쉬움 | 영속성 컨텍스트, 변경 감지, 지연 로딩 등 추가 기능이 있음 |

[14:22] 최근 트렌드
[14:22] - Spring Data JPA를 기본으로 쓰고, 복잡한 조회·통계·대용량 배치는 JdbcTemplate, MyBatis, Querydsl로 보완하는 하이브리드 방식이 주류
[14:22] - JPA의 무거운 추상화 대신 단순한 매핑을 원하면 Spring Data JDBC를 쓰기도 한다

[14:22] JPA를 많이 쓰는 이유
[14:22] - 생산성·유지보수: 컬럼이 바뀔 때마다 SQL과 매핑 코드를 일일이 고치지 않아도 된다
[14:22] - 객체지향 도메인 모델링: 비즈니스 규칙을 Entity 중심으로 표현 (DDD와 잘 맞음)
[14:22] - 영속성 컨텍스트: 1차 캐시, 커밋 시점 변경 감지(Dirty Checking), 쓰기 지연
[14:22] - 표준 명세(jakarta.persistence)라 특정 DB에 덜 묶이고, Spring의 트랜잭션·테스트 생태계와 잘 맞는다

[14:22] ### 커넥션 풀링과 HikariCP
[14:22] - 커넥션 풀링: DB 연결을 요청마다 새로 만들지 않고, 미리 몇 개 만들어 풀에 두고 빌려 쓰고 반납하는 방식
[14:22] - 왜 필요한가: DB 연결 한 번에 네트워크 왕복(TCP 핸드셰이크, 인증)과 DB 세션 생성이 들어간다
[14:22] - 응답 지연 감소: 이미 만든 연결을 재사용
[14:22] - DB 보호: 풀 크기로 동시 연결 수를 제한해서 DB 메모리·스레드 고갈 방지
[14:22] - 자원 재활용: 연결을 닫지 않고 반납해서 생성·종료 반복 낭비를 줄임

[14:22] HikariCP: Spring Boot 기본 커넥션 풀 (이 프로젝트: spring-boot-starter-data-jpa → spring-boot-starter-jdbc → HikariCP 7.0.2)
[14:22] - DataSource 구현체로 커넥션 대여·반납 관리
[14:22] - 풀 크기·대기 시간: minimumIdle, maximumPoolSize, connectionTimeout
[14:22] - 끊어진 커넥션 검사, 수명 관리: maxLifetime, idleTimeout
[14:22] - 누수 감지: leakDetectionThreshold, Micrometer로 활성/유휴 커넥션 수 같은 지표 수집
[14:22] - 바이트코드 최적화, 가벼운 자료구조(ConcurrentBag)로 락 경합과 오버헤드를 줄임

[14:22] HikariCP 말고 다른 커넥션 풀

[14:22] | 오픈소스 | 특징 | 주로 쓰는 곳 |
[14:22] | --- | --- | --- |
[14:22] | Apache Commons DBCP2 | 오래되고 검증된 Apache 계열 풀 | 레거시, 기존 Apache 구성 유지 |
[14:22] | Tomcat JDBC Pool | Spring Boot 1.x 기본 풀, DBCP보다 동시성 개선 | Tomcat 연동, 1.x 구성 유지 |

[14:22] | c3p0 | 오래된 JDBC 풀 | 레거시 유지보수 (신규 도입은 줄어드는 추세) |
[14:22] | Agroal / Oracle UCP | Quarkus 같은 최신 런타임, Oracle 전용 기능(RAC, 페일오버) | 특정 런타임, Oracle 환경 |

[14:22] 스프링부트가 HikariCP를 고른 이유 (Boot 2.0부터 Tomcat JDBC Pool → HikariCP)

[14:22] - 가볍다: 라이브러리가 작고 핵심 기능에 집중해서 기본 스타터에 넣기 부담이 없다

[14:22] - 설계가 절제돼 있다: 풀링 본연의 역할에 충실 → Spring Boot의 "합리적인 기본값" 철학과 맞는다
