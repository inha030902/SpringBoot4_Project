### Jackson
- Java 객체와 JSON(그 외 YAML, XML 등) 사이의 직렬화·역직렬화를 맡는 데이터 바인딩 라이브러리
  - 직렬화: Java 객체(DTO, Entity) → JSON 문자열. REST API가 응답을 JSON으로 내려줄 때
  - 역직렬화: JSON 문자열 → Java 객체. @RequestBody로 요청 본문을 받을 때 내부에서 동작
- 어노테이션으로 세밀하게 제어
  - @JsonProperty: 필드명 매핑 / @JsonIgnore: 민감 정보 노출 차단 / @JsonFormat: 날짜 포맷
- DTO 없이도 ObjectMapper와 JsonNode(트리 모델)로 JSON을 동적으로 읽고 수정·생성할 수 있다

### Tomcat
- Java 기반 웹 컨테이너(서블릿 컨테이너)이자 경량 WAS
- HTTP 요청을 받아 Java 웹 애플리케이션(서블릿, Spring MVC)을 실행하고 응답을 돌려준다
  - HTTP 통신 처리, 커넥션 풀·스레드 풀 관리로 동시 요청 처리
  - 요청을 서블릿(Spring MVC의 DispatcherServlet)에 넘기고 응답을 HTTP로 반환
  - 서블릿·필터의 생명주기(초기화 → 요청 처리 → 소멸) 관리

Web Server와 Web Container는 다르다

| 구분 | Web Server | Web Container |
| --- | --- | --- |
| 핵심 역할 | HTML, CSS, JS, 이미지 같은 정적 파일 제공, 리버스 프록시·로드 밸런싱 | 서블릿·JSP 같은 동적 Java 코드 실행, 생명주기 관리 |
| 처리 방식 | 파일을 읽어 그대로 반환 | 비즈니스 로직·DB 조회를 수행해서 결과를 만든다 |
| 대표 예시 | Nginx, Apache HTTP Server | Apache Tomcat, Jetty, Undertow |

스프링부트에서 Tomcat 의존성을 추가해야 하나? → 추가 안 해도 된다

## 2교시 (10:05~10:55)
### JDBC
- JDBC(Java Database Connectivity): Java 애플리케이션이 DB에 접속해 SQL을 실행하고 결과를 처리하는 표준 API
- DB마다(MySQL, MariaDB, Oracle…) 통신 방식과 드라이버는 다르지만, 개발자는 같은 인터페이스(Connection, Statement, PreparedStatement, ResultSet)로 접근한다
  - 표준 인터페이스: java.sql, javax.sql
  - 각 DB 회사가 이 인터페이스를 구현한 JDBC 드라이버를 제공 (이 프로젝트: MariaDB Driver, H2)
  - SQL 문법·벤더 고유 기능만 빼면 코드를 크게 안 바꾸고 다른 DB로 옮길 수 있다

기본 흐름
1. 커넥션 얻기: DataSource(또는 DriverManager)로 Connection을 가져온다
2. SQL 실행: PreparedStatement 등으로 실행 (조회면 ResultSet, 갱신이면 바뀐 행 수)
3. 결과 처리·트랜잭션: 결과를 읽고 필요하면 commit / rollback
4. 자원 반납: ResultSet, Statement, Connection을 닫거나 커넥션 풀에 반납 → 리소스 누수 방지

스프링부트에서는
- 순수 JDBC를 매번 쓰기보다 JdbcTemplate, JPA/Hibernate, MyBatis 같은 상위 기술을 주로 쓴다
- spring-boot-starter-jdbc나 spring-boot-starter-data-jpa에 HikariCP가 들어 있어서 application.properties에 DB 접속 정보만 적으면 DataSource가 자동 구성된다

### JDBC와 JPA의 차이
- JDBC: SQL을 직접 쓰고 실행하는 저수준 표준 API
- JPA: Java 객체와 DB 테이블을 매핑해서 SQL 작성을 자동화하는 ORM 표준 명세 (대표 구현체: Hibernate)

| 구분 | JDBC (JdbcTemplate) | JPA (Hibernate) |
| --- | --- | --- |
| 추상화 수준 | 낮음. SQL, 파라미터 바인딩, 결과 매핑을 직접 | 높음. 엔티티 객체 중심, SQL은 프레임워크가 생성 |
| 객체-테이블 불일치 | 개발자가 직접 변환 | 연관관계, 상속, 영속성 컨텍스트로 완화 |
| 반복 코드 | PreparedStatement, ResultSet 처리가 많음 | Repository, 메서드 이름 규칙으로 CRUD를 크게 줄임 |
| 쿼리 제어 | 복잡한 조인·통계·튜닝이 직관적 | 단순 CRUD는 빠르지만 복잡한 쿼리·대량 처리는 보완 필요 |
| 오버헤드 | 가볍고 동작 예측이 쉬움 | 영속성 컨텍스트, 변경 감지, 지연 로딩 등 추가 기능이 있음 |

최근 트렌드
- Spring Data JPA를 기본으로 쓰고, 복잡한 조회·통계·대용량 배치는 JdbcTemplate, MyBatis, Querydsl로 보완하는 하이브리드 방식이 주류
- JPA의 무거운 추상화 대신 단순한 매핑을 원하면 Spring Data JDBC를 쓰기도 한다

JPA를 많이 쓰는 이유
- 생산성·유지보수: 컬럼이 바뀔 때마다 SQL과 매핑 코드를 일일이 고치지 않아도 된다
- 객체지향 도메인 모델링: 비즈니스 규칙을 Entity 중심으로 표현 (DDD와 잘 맞음)
- 영속성 컨텍스트: 1차 캐시, 커밋 시점 변경 감지(Dirty Checking), 쓰기 지연
- 표준 명세(jakarta.persistence)라 특정 DB에 덜 묶이고, Spring의 트랜잭션·테스트 생태계와 잘 맞는다

## 3교시 (11:00~11:30)
### 커넥션 풀링과 HikariCP
- 커넥션 풀링: DB 연결을 요청마다 새로 만들지 않고, 미리 몇 개 만들어 풀에 두고 빌려 쓰고 반납하는 방식
- 왜 필요한가: DB 연결 한 번에 네트워크 왕복(TCP 핸드셰이크, 인증)과 DB 세션 생성이 들어간다
  - 응답 지연 감소: 이미 만든 연결을 재사용
  - DB 보호: 풀 크기로 동시 연결 수를 제한해서 DB 메모리·스레드 고갈 방지
  - 자원 재활용: 연결을 닫지 않고 반납해서 생성·종료 반복 낭비를 줄임

HikariCP: Spring Boot 기본 커넥션 풀 (이 프로젝트: spring-boot-starter-data-jpa → spring-boot-starter-jdbc → HikariCP 7.0.2)
- DataSource 구현체로 커넥션 대여·반납 관리
- 풀 크기·대기 시간: minimumIdle, maximumPoolSize, connectionTimeout
- 끊어진 커넥션 검사, 수명 관리: maxLifetime, idleTimeout
- 누수 감지: leakDetectionThreshold, Micrometer로 활성/유휴 커넥션 수 같은 지표 수집
- 바이트코드 최적화, 가벼운 자료구조(ConcurrentBag)로 락 경합과 오버헤드를 줄임

HikariCP 말고 다른 커넥션 풀

| 오픈소스 | 특징 | 주로 쓰는 곳 |
| --- | --- | --- |
| Apache Commons DBCP2 | 오래되고 검증된 Apache 계열 풀 | 레거시, 기존 Apache 구성 유지 |
| Tomcat JDBC Pool | Spring Boot 1.x 기본 풀, DBCP보다 동시성 개선 | Tomcat 연동, 1.x 구성 유지 |
| Alibaba Druid | SQL 필터링, 모니터링 통계 등 부가 기능이 많음 | SQL 감사·모니터링이 필요한 곳 |
| c3p0 | 오래된 JDBC 풀 | 레거시 유지보수 (신규 도입은 줄어드는 추세) |
| Agroal / Oracle UCP | Quarkus 같은 최신 런타임, Oracle 전용 기능(RAC, 페일오버) | 특정 런타임, Oracle 환경 |

스프링부트가 HikariCP를 고른 이유 (Boot 2.0부터 Tomcat JDBC Pool → HikariCP)
- 빠르다: 동기화·락 경합을 줄여서 대여·반납 지연과 CPU·메모리 부담이 작다
- 가볍다: 라이브러리가 작고 핵심 기능에 집중해서 기본 스타터에 넣기 부담이 없다
- 안정적: 유효성 검사, 수명 관리, 누수 감지 같은 운영 기능을 깔끔하게 제공
- 설계가 절제돼 있다: 풀링 본연의 역할에 충실 → Spring Boot의 "합리적인 기본값" 철학과 맞는다

### 시작 클래스와 첫 Runner (13:43 커밋)
- @SpringBootApplication = @Configuration + @ComponentScan + @EnableAutoConfiguration
  - 시작 클래스가 설정 클래스라서 안에 @Bean 메서드를 둘 수 있다 → helloBean()으로 "Hello 스프링부트" 문자열을 빈으로 등록해 봄 (14:48에 지움)
- DBRunner: ApplicationRunner를 구현하고 @Component를 붙이면, 앱이 다 뜬 뒤 run()이 자동으로 실행된다
  - @Autowired로 DataSource를 주입받아 구현 클래스 이름을 출력
  - HikariCP가 들어 있어서 com.zaxxer.hikari.HikariDataSource가 나온다 (3교시 HikariCP 내용과 연결)

```java
@Component
public class DBRunner implements ApplicationRunner {
    @Autowired
    DataSource dataSource;

    @Override
    public void run(ApplicationArguments args) throws Exception {
        System.out.println("DataSource 구현 클래스 이름 = " + dataSource.getClass().getName());
    }
}
```

### 환경 변수(프로퍼티) 읽기
- application.properties에 내가 만든 값 추가: myboot.name = Spring (server.port = 8080은 주석으로)
- @Value("${myboot.name}")로 필드에 주입
- ApplicationArguments.containsOption("이름"): 실행할 때 프로그램 인자 --이름=값 으로 넘어왔는지 확인

```java
@Value("${myboot.name}")
String myBootName;

@Override
public void run(ApplicationArguments args) throws Exception {
    System.out.println("환경변수 myboot.name = " + myBootName);
    System.out.println("server.port VM argument 환경변수 확인 " + args.containsOption("server.port"));
    System.out.println("myboot.name Program 환경변수 확인 " + args.containsOption("myboot.name"));
}
```

VM argument와 Program argument (IntelliJ 실행 구성)

| 구분 | 넣는 방법 | containsOption |
| --- | --- | --- |
| VM argument | -Dserver.port=8088 | false (JVM 시스템 프로퍼티라 프로그램 인자가 아님) |
| Program argument | --myboot.name=Boot | true |

- 둘 다 Spring 환경 값에는 반영된다 (포트가 바뀌고, @Value 값도 바뀜)
- 우선순위: 프로그램 인자 > VM 인자(시스템 프로퍼티) > application.properties

## 7교시 (16:10~17:00)
### 넘어온 프로그램 인자 목록 보기 (16:26~16:51 커밋, MyRunner)
- args.getOptionNames(): 프로그램 인자(--이름=값)로 넘어온 이름들을 Set<String>으로 돌려준다
  - VM argument(-D...)는 프로그램 인자가 아니라서 여기에 안 나온다 (6교시 containsOption과 같은 이유)
- 같은 목록을 세 가지 방법으로 출력해 봄

```java
Set<String> optionNames = args.getOptionNames();

// 1) 기존의 for loop
for (String name : optionNames) {
    System.out.println("name = " + name);
}

// 2) 람다식
optionNames.forEach(optionName -> System.out.println(optionName));

// 3) 메서드 레퍼런스
optionNames.forEach(System.out::println);
```

### forEach와 Consumer
- forEach는 Iterable의 default 메서드: `default void forEach(Consumer<? super T> action)`
- Consumer = 함수형 인터페이스(추상 메서드가 하나뿐인 인터페이스). 그 추상 메서드는 `void accept(T t)`: 값을 받아서 쓰기만 하고 돌려주지 않는다
- 람다식 `optionName -> System.out.println(optionName)`이 accept()의 구현이 된다
- 람다가 받은 값을 그대로 다른 메서드에 넘기기만 하면 메서드 레퍼런스 `System.out::println`으로 줄여 쓸 수 있다

### 그 밖에
- run() 메서드의 닫는 중괄호 `}`가 println 세 줄 바로 뒤에 있어서, 아래 코드가 메서드 밖으로 나가 컴파일 에러가 났다 (illegal start of type, <identifier> expected) → `}`를 forEach 아래로 옮겨서 해결
