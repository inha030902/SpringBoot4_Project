### 질문: 인터페이스 메서드를 Inner Class로 구현하는 경우 / Consumer를 단계별로 줄이기

- `Iterable`의 `default void forEach(Consumer<? super T> action)`
  - 컬렉션 요소를 하나씩 꺼내 `action.accept(요소)`를 부름
- `Consumer<T>`: `void accept(T t)` 하나뿐인 함수형 인터페이스 (받기만 하고 반환 없음)
- 이너 클래스를 쓰는 이유: 그 클래스 안에서만 쓰는 구현체라서 최상위 클래스를 따로 만들지 않으려고. 바깥 클래스의 필드·메서드에도 바로 접근 가능

### 4단계로 줄이기 (예: `names.forEach(...)`로 이름 출력)

```java
// 1) 이름 있는 이너 클래스
private class PrintConsumer implements Consumer<String> {
    @Override
    public void accept(String name) { System.out.println(name); }
}
names.forEach(new PrintConsumer());

// 2) 익명 이너 클래스: 선언과 생성을 인자 자리에서 한 번에
names.forEach(new Consumer<String>() {
    @Override
    public void accept(String name) { System.out.println(name); }
});

// 3) 람다: 인터페이스 이름, 메서드 이름(accept), 반환 타입 생략
names.forEach(name -> System.out.println(name));

// 4) 메서드 레퍼런스: 받은 값을 그대로 넘기기만 할 때
names.forEach(System.out::println);
```

| 방식 | 언제 쓰나 |
| --- | --- |
| 이름 있는 이너 클래스 | 로직이 길거나, 필드(상태)를 갖거나, 여러 곳에서 재사용 |
| 익명 이너 클래스 | 추상 메서드가 여러 개라 람다를 못 쓸 때 |
| 람다 | 한 번 쓰는 콜백, 조건문 등 직접 로직이 있을 때 |
| 메서드 레퍼런스 | 기존 메서드 호출만 할 때 |

- 주의: 람다 안에서 쓰는 바깥 지역 변수는 사실상 final(effectively final)이어야 함
- 어제 MyRunner의 `optionNames.forEach(...)`가 3·4단계

### HibernateProperties: `spring.jpa.hibernate.*` 설정을 담는 클래스

- `@ConfigurationProperties("spring.jpa.hibernate")`가 붙은 클래스
  - properties 파일에서 `spring.jpa.hibernate.`로 시작하는 값을 필드에 자동으로 넣어 줌 (앞에서 배운 `@Value`를 묶음으로 처리하는 방식)
- 위치는 버전에 따라 다름
  - Boot 3.5: `org.springframework.boot.autoconfigure.orm.jpa.HibernateProperties`
  - Boot 4.0(우리 프로젝트): `org.springframework.boot.hibernate.autoconfigure.HibernateProperties` (`spring-boot-hibernate` 모듈로 분리됨)

| 필드 | properties 키 | 뜻 |
| --- | --- | --- |
| `ddlAuto` | `spring.jpa.hibernate.ddl-auto` | 앱 시작 시 테이블 처리 방법 (`none`, `validate`, `update`, `create`, `create-drop`) |
| `naming.physicalStrategy` | `spring.jpa.hibernate.naming.physical-strategy` | 엔티티 이름 → DB 테이블·컬럼 이름 변환 규칙 |
| `naming.implicitStrategy` | `spring.jpa.hibernate.naming.implicit-strategy` | 이름을 직접 지정하지 않았을 때 정하는 규칙 |

```properties
spring.jpa.hibernate.ddl-auto=create
```

- `determineHibernateProperties(...)`: 표준 JPA 설정(`spring.jpa.properties.*`)과 위 값을 합쳐 Hibernate `EntityManagerFactory`를 만들 때 쓸 최종 설정 Map을 만듦
- 짝꿍 클래스 `JpaProperties`(`spring.jpa.*`): `show-sql`, `database-platform`, `open-in-view`, `properties` 등 JPA 공통 설정
- ddl-auto를 안 적으면: H2 같은 내장 DB는 `create-drop`, 그 밖의 DB는 `none`
- 참고: [HibernateProperties API (3.5)](https://docs.spring.io/spring-boot/3.5/api/java/org/springframework/boot/autoconfigure/orm/jpa/HibernateProperties.html)

### MyBootProperties: 내 설정값을 객체 하나로 묶기

HibernateProperties와 같은 방식으로 `myboot.*` 값을 담는 클래스를 직접 만듦.

```java
@Component                              // 빈으로 등록해야 주입받을 수 있음
@ConfigurationProperties("myboot")      // myboot.로 시작하는 값을 필드에 넣어 줌
@Getter @Setter                         // 값을 넣을 때 setter가 쓰임
public class MyBootProperties {
    private String name;      // myboot.name
    private int age;          // myboot.age (문자열 → int 자동 변환)
    private String fullName;  // myboot.fullName (full-name으로 써도 연결됨)
}
```

```java
// MyRunner에서 사용
@Autowired
MyBootProperties properties;

System.out.println("MyBootProperties getName() = " + properties.getFullName());
System.out.println("MyBootProperties getAge() = " + properties.getAge());
```

- 주의: 첫 줄 문구는 `getName()`인데 실제로는 `getFullName()`을 부름 → "Spring Boot"처럼 전체 이름이 나옴
- Run Configuration의 `--myboot.name=스프링`이 더 우선이라 이 값도 "스프링 Boot"로 나옴

| 방법 | 쓰는 법 | 특징 |
| --- | --- | --- |
| `@Value` | `@Value("${myboot.name}")` | 값 하나씩, 키 이름을 문자열로 적음 |
| `Environment` | `environment.getProperty("myboot.fullName")` | 실행 중에 키로 꺼냄, 반환은 문자열 |
| `@ConfigurationProperties` | 클래스에 prefix 지정 | 여러 값을 객체로 묶음, 타입 변환, 재사용 쉬움 |

- `spring-boot-configuration-processor` (`<optional>true</optional>`)
  - `@ConfigurationProperties` 클래스를 보고 설정 키 목록(`spring-configuration-metadata.json`)을 만들어 줌 → properties 파일에서 `myboot.` 자동완성
  - `optional`: 컴파일할 때만 쓰고 다른 프로젝트로는 전달되지 않음
  - 우리 pom은 `annotationProcessorPaths`에 lombok만 있어서 Maven 빌드 때는 이 파일이 안 생김

## 파트3 (11:00~11:30)
### 질문: 스프링부트 프로파일(Profile)이란? 왜 필요한가?

- 프로파일 = 환경(local, dev, prod)별로 설정이나 빈을 다르게 적용하게 해 주는 이름표
- 환경마다 달라지는 것: DB 주소·계정, 외부 API 키(테스트용 vs 실제), 로그 수준, 기능 on/off

#### 1) 환경별 설정 파일 분리

```
src/main/resources/
├── application.properties         ← 공통 설정 + 어떤 프로파일을 쓸지
├── application-local.properties   ← 내 PC: 로컬 DB, 상세 로그
├── application-dev.properties     ← 개발 서버: 개발 DB, 테스트 API 키
└── application-prod.properties    ← 운영 서버: 운영 DB, 민감 정보는 환경변수로
```

- 공통 값은 `application.properties`, 환경마다 바뀌는 값만 `application-{프로파일}.properties`에 둠
- 같은 키가 있으면 활성화된 프로파일 파일의 값이 우선

#### 2) 환경별 빈 등록 (`@Profile`)

활성화된 프로파일에 따라 그 클래스·메서드를 빈으로 등록할지 정함. 예: 알림 발송

```java
public interface NotificationSender {
    void send(String to, String message);
}

@Component
@Profile({"local", "dev"})   // local 또는 dev일 때만 등록
public class DummyNotificationSender implements NotificationSender {
    public void send(String to, String message) {
        System.out.println("[테스트 발송 - 실제 전송 안 됨] " + to + ": " + message);
    }
}

@Component
@Profile("prod")             // prod일 때만 등록
public class RealEmailNotificationSender implements NotificationSender {
    public void send(String to, String message) { /* 실제 SMTP·API 호출 */ }
}
```

```java
@Service
public class OrderService {
    private final NotificationSender notificationSender;   // 인터페이스만 앎

    public OrderService(NotificationSender notificationSender) {   // 프로파일에 맞는 구현체가 주입됨
        this.notificationSender = notificationSender;
    }
}
```

- `local`로 실행 → Dummy가 주입되어 콘솔에만 찍힘 / `prod`로 실행 → Real이 주입되어 실제 발송
- 서비스 코드는 그대로, 프로파일만 바꿔서 구현체 교체

`@Bean` 메서드에도 붙일 수 있음 (외부 라이브러리 객체처럼 `@Component`를 못 붙일 때)

```java
@Configuration
public class PaymentConfig {
    @Bean @Profile("!prod")   // prod가 아닐 때
    public PaymentClient mockPaymentClient() { return new MockPaymentClient(); }

    @Bean @Profile("prod")
    public PaymentClient pgPaymentClient() { return new RealPgPaymentClient(); }
}
```

- 주의: 프로파일을 안 켜면 `default`만 활성화 → `@Profile("prod")` 빈만 있으면 주입할 빈이 없어 `NoSuchBeanDefinitionException`
  - 해결: `!prod`처럼 기본 상황에서도 등록되는 구현체를 함께 둠
- `!` = "그 프로파일이 아닐 때"

#### 3) 프로파일 켜기

```properties
# application.properties
spring.profiles.active=local
```

- 실행할 때 바꾸기: `--spring.profiles.active=prod` (program argument) 또는 환경변수 `SPRING_PROFILES_ACTIVE=prod`
- 오늘 배운 우선순위대로 program argument가 properties 파일보다 우선

#### 왜 필요한가
- 운영 주소를 주석으로 바꿔 가며 고치다가 운영 DB에 테스트 데이터를 넣는 사고를 막음
- 같은 jar(`myboot4.jar`) 하나를 실행 옵션만 바꿔 여러 환경에 배포할 수 있음
- 처음에는 local과 prod 두 개만 나눠 보면 충분함

### 로깅(Logging): `System.out.println` 대신 Logger 쓰기

- 스프링 부트에는 SLF4J(인터페이스) + Logback(구현체)이 기본 포함 → 의존성 추가 없이 바로 사용
- 코드는 SLF4J에만 의존 → 나중에 구현체를 바꿔도 코드 수정 없음

#### 1) MyRunner에 Logger 적용

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

// Logger 객체 생성 (클래스 이름이 로그에 함께 찍힘)
Logger logger = LoggerFactory.getLogger(MyRunner.class);

System.out.println("Logger 구현 클래스명 = " + logger.getClass().getName());
// → ch.qos.logback.classic.Logger  (실제 구현체는 Logback)

logger.debug("CustomerVO = {}", customVO);
logger.debug("환경변수 myboot.name = {}", myBootName);
logger.info("MyBootProperties getAge() = {}", properties.getAge());
logger.info("server.port Program argument 확인 {}", args.containsOption("server.port"));
```

- `{}` 자리에 뒤의 값이 순서대로 들어감
- `+`로 이어 붙이면 로그가 꺼져 있어도 문자열을 만듦 → `{}`는 실제로 찍을 때만 만들어서 더 효율적
- println과 달리 시간, 레벨, 스레드, 클래스 이름이 자동으로 붙음

#### 2) 로그 레벨

```
낮음  TRACE < DEBUG < INFO < WARN < ERROR  높음
```

- 설정한 레벨 **이상**만 출력됨 (레벨을 낮게 잡을수록 많이 보임)
- 스프링 부트 기본값은 INFO → 설정 안 하면 `logger.debug()`는 안 보임

| 설정 레벨 | 보이는 로그 |
|---|---|
| DEBUG | debug, info, warn, error |
| INFO | info, warn, error |
| WARN | warn, error |

#### 3) 프로파일별로 로그 레벨 다르게

```properties
# application-test.properties  ← 개발·테스트: 자세히
logging.level.com.inspirecamp7.myspringbootproject4 = DEBUG

# application-prod.properties  ← 운영: 꼭 필요한 것만
logging.level.com.inspirecamp7.myspringbootproject4 = INFO
```

- `logging.level.{패키지명}` → 그 패키지 아래 클래스에만 적용 (스프링 내부 로그는 그대로 INFO)
- `test`로 실행 → debug + info 모두 출력
- `prod`로 실행 → info만 출력, debug 줄은 안 보임
- 파트3의 "환경마다 달라지는 것: 로그 수준"을 직접 해 본 것

#### 4) 로그를 파일로 남기기

```properties
# application.properties
spring.profiles.active = prod
logging.file.path = logs/
```

- 실행하면 프로젝트 폴더에 `logs/spring.log` 파일이 생기고 콘솔과 같은 로그가 쌓임
- 서버를 재시작해도 기록이 남음 → 운영에서 장애 추적할 때 필요
- 로그 파일은 GitHub에 올릴 필요 없음 → `.gitignore`에 `logs/` 추가

#### 정리: application.properties 역할 나누기

- 공통 값(`myboot.name`, 활성 프로파일, 로그 파일 경로)만 `application.properties`에 남김
- 환경마다 다른 값(`myboot.age`, `myboot.fullName`, 로그 레벨)은 `application-test/prod.properties`로 옮김
